## 1 Назначение и границы документа

Этот документ нужен для того, чтобы проект развивался как система, а не как набор независимых экранов. Он объясняет, где находится источник истины для алгоритмов, где хранится учебное содержание, как данные идут от клика ученика до кабинета учителя и какие части нельзя менять без согласованной проверки.

Документ рассчитан на четыре ситуации:

- автор использует его перед изменением кода;
- руководительница получает понятную картину готовности дипломного прототипа;
- учитель понимает, что происходит на каждом экране;
- новый разработчик видит точки расширения и ограничения, не изучая весь репозиторий с нуля.

В обзор входят браузерный интерфейс, алгоритмическое ядро, учебное содержание, локальное хранение, Node.js и SQLite, роли учителя и ученика, Python runner, миссия BFS, Docker и GitHub Pages. В обзор не входит доказательство соответствия государственным требованиям или полноценное исследование учебной эффективности: для этого нужны отдельные методические и пользовательские исследования.

## 3 Архитектура по слоям

Платформа — монолит с разделением ответственности. Браузер получает интерфейс и выполняет визуализацию. Node.js обслуживает аккаунты, классы и сохранённые работы. SQLite хранит серверные данные. Caddy отвечает за HTTPS. Статическое демо намеренно работает без API и аккаунтов.

| Слой | Главная ответственность | Источник истины | Нельзя делать |
|---|---|---|---|
| Учебное содержание | Занятия, цели, вопросы, задания и Python-шаблоны | `public/course.js` и локализация | Дублировать тексты в обработчиках |
| Домен графов | Граф, валидация, соседство, трассировка, проверка пути | `public/core.js` | Добавлять DOM, storage или сеть в ядро |
| Представление | Маршруты, экраны, кнопки, SVG и выбранный шаг | `public/app.js`, view и CSS | Пересчитывать алгоритм только ради показа |
| Состояние браузера | Гость, черновики, прогресс, миссии и граф ученика | `localStorage` через storage-state | Считать его серверной оценкой |
| Сервер | API, сессии, роли, классы, проверки и SQLite | `server.mjs` и конфигурация | Доверять `userId` или `classId` из браузера |
| Выполнение Python | Изолированный iframe и Worker в браузере | `runner.html`, `runner.js`, Worker | Запускать ученический код внутри API |
| Размещение | Docker, Caddy, backup и GitHub Pages | `compose.yaml`, `Dockerfile`, scripts | Публиковать app или базу напрямую |

### 3.1 Поток статического демо

1. Пользователь открывает публичный URL GitHub Pages.
2. Pages отдаёт статические HTML, CSS и JS из собранной папки `.pages-site`.
3. `site-config.js` включает статический режим, поэтому `app.js` не вызывает API для аккаунта.
4. Курс, миссия и прогресс работают в браузере. Черновики гостя не синхронизируются с учителем.
5. Python загружает Pyodide с CDN и запускается в браузере. Для первого запуска нужен интернет.

### 3.2 Поток локального сервера

1. `START.cmd` или `node server.mjs` запускает приложение на `127.0.0.1:4318` и runner на `127.0.0.1:4319`.
2. `app.js` вызывает `/api/me` и получает пользователя, CSRF-токен, прогресс, классы и назначения.
3. Изменяющие запросы отправляют CSRF-токен; сервер проверяет Origin, роль и принадлежность объекта.
4. SQLite хранится в `.local/classroom.sqlite`. База не входит в Git и Pages-артефакт.
5. Локальные черновики и миссия всё равно остаются в браузере; серверные результаты появляются после явного сохранения.

### 3.3 Поток серверного пилота

1. Caddy принимает HTTPS на двух разных именах: одно для приложения, второе для Python runner.
2. HTTP Basic закрывает внешний вход в демо. Внутри платформы отдельные аккаунты определяют роль.
3. `app` работает одним экземпляром и пишет SQLite в постоянный том.
4. `backup` делает согласованные снимки базы в отдельном томе; копии нужно уносить за пределы VPS.
5. Администратор проверяет healthcheck, логи, свободное место и восстановление до допуска реальных участников.

## 5 Модель данных и жизненный цикл результата

### 5.1 Граф

Граф содержит `directed`, `nodes` и `edges`. Вершина имеет `id`, `x` и `y`. Ребро имеет `a`, `b` и положительный вес `w`. Валидация допускает от 2 до 12 вершин, не более 40 рёбер, уникальные идентификаторы от 1 до 99 и веса от 1 до 99. Положение вершины влияет на рисунок, но не на стоимость пути.

### 5.2 Снимок алгоритма

`trace` возвращает последовательность независимых снимков. В снимке есть текущая вершина, очередь или стек, завершённые вершины, порядок, расстояния, предшественники, активные рёбра, итоговый путь, счётчики, псевдокод, заголовок и объяснение. UI выбирает снимок по индексу истории. Поэтому шаг назад — это возврат к предыдущему состоянию, а не попытка обратить алгоритм.

| Событие | Что видит ученик | Что проверять |
|---|---|---|
| BFS visit | Текущая вершина, очередь и новые соседи | Новые вершины добавляются один раз и в порядке номеров |
| DFS enter, descend, skip, return | Стек вызовов, переход, пропуск и возврат | Рекурсия не зацикливается, возврат восстанавливает контекст |
| Dijkstra select, relax, settle | Минимальное расстояние и обновление соседа | Сравнивается сумма весов, а не длина линии |
| done | Порядок, недостижимость или итоговый путь | Результат согласован с независимым оракулом |

### 5.3 Серверные таблицы

| Таблица | Назначение | Кто видит |
|---|---|---|
| `users` | Логин, имя, роль, соль и производное пароля | Свой профиль; сервер использует роль |
| `sessions` | Хэш токена, CSRF и срок действия | Только сервер |
| `classes`, `members` | Класс учителя и участники по коду | Учитель своего класса; ученик свои классы |
| `assignments` | Назначенные классу занятия | Учитель своего класса; ученик свои назначения |
| `attempts` | Ответы, баллы и время | Ученик свои; учитель своего класса |
| `submissions` | Последняя Python-работа, пояснение и отчёт | Ученик свои; учитель своего класса |
| `feedback` | Комментарий учителя к работе | Ученик адресата и учитель своего класса |

Ограничение модели: `submissions` хранит последнюю работу по занятию и перезаписывает предыдущую версию. Истории отправок, журнала изменений и полноценного аудита учителя пока нет. Для школьной эксплуатации это нужно решить до использования оценочных работ.

### 5.4 Где что сохраняется

| Режим | В браузере | На сервере | Ограничение |
|---|---|---|---|
| Pages демо | Прогресс, черновики, миссия, граф ученика | Ничего | Нет аккаунтов, классов и отправки учителю |
| Локальный сервер | Черновики и гостевая миссия | SQLite в `.local` | Данные доступны только на этом компьютере |
| Docker пилот | Черновики текущего браузера | SQLite в volume `/data` | Нужны backup, внешний доступ и политика хранения |

## 6 Алгоритмическое ядро и визуализация

### 6.1 BFS

BFS начинает с выбранной вершины, кладёт её в очередь, достаёт вершины слева направо и добавляет ещё не открытых соседей. Для учебного показа обработка вершины объединяется в один шаг. Рядом с графом видно, какая вершина обработана, какие соседи добавлены и что находится в очереди.

### 6.2 DFS

DFS показывает стек рекурсивных вызовов. Снимки отдельно отображают вход, переход к соседу, пропуск уже открытого соседа и возврат. Ученик видит не только итоговый порядок, но и момент возврата к прежнему вызову.

### 6.3 Кратчайший путь

Режим `path` использует BFS и считает число переходов. Режим `dijkstra` хранит суммы положительных весов и выбирает минимальное ещё не обработанное расстояние. Восстановление пути выполняется по `parent`. Проверка допускает любой оптимальный маршрут, если стоимость совпадает с эталоном.

### 6.4 2D и 3D

SVG показывает граф, подписи и семантические состояния вершины. 3D меняет положение и камеру, но не граф и не последовательность шагов. Перемещение вершины в 3D не меняет связи. Это нужно объяснять ученику, потому что близкая точка на рисунке не означает маленький вес.

**Архитектурное преимущество:** алгоритм можно тестировать без браузера, а визуальный слой менять без переписывания BFS, DFS или Дейкстры.

### 7.2 Автор или архитектор

В продукте нет отдельной административной роли. Архитектор управляет репозиторием, версиями, настройками размещения, секретами, резервными копиями и правилами изменения. Это внешняя техническая ответственность.

- Сохраняет независимость алгоритмического ядра от DOM и сети.
- Проверяет миграции базы, права доступа, Pages-режим и Docker-конфигурацию.
- Решает, является ли функция частью пилота или только экспериментом.
- Не передаёт реальные данные школьников в GitHub, Issues или скриншоты.
- После релиза фиксирует версию, изменения, тесты и известные ограничения.

### 7.3 Учитель

1. Открывает карту курса и смотрит пять разделов.
2. Создаёт тестовый аккаунт с ролью учителя в серверной версии.
3. Создаёт класс и передаёт ученику код приглашения.
4. Назначает занятие, например 21 «Пишем BFS на Python».
5. Открывает результат ученика, читает код и пояснение, оставляет комментарий.
6. Использует карту и уроки для объяснения на экране. Автоматическая самопроверка не заменяет учительскую оценку.

### 7.4 Ученик

1. Начинает с «С чего начать» или первой карточки карты курса.
2. Меняет граф, прокручивает шаги назад и вперёд и предсказывает следующий шаг.
3. Переходит в тренировку, отвечает на вопросы и читает объяснение ошибки.
4. В миссии BFS сам выбирает вершины очереди, исправляет ошибки и строит маршрут.
5. В Python пишет решение или открывает пример, запускает проверки и добавляет пояснение.
6. Нажимает отдельную кнопку сохранения работы для учителя. Авточерновик не является отправкой.

### 7.5 Руководительница или рецензент

Для первого просмотра достаточно статической ссылки: регистрация и установка Node.js не нужны. Рецензент проверяет понятность структуры, корректность терминов, читаемость графа, пользу миссии и связь визуализации с целью урока. Для проверки ролей нужен локальный сервер или закрытый HTTPS-пилот с двумя отдельными профилями браузера.

- Docker Compose с `app`, `backup` и Caddy; отдельные HTTPS-имена для приложения и runner.
- Автоматические тесты алгоритмов, сервера, миссии, локализации, Pages и резервного копирования.

Последний зафиксированный технический срез прошёл 71 автоматический тест. Это подтверждает поведение кода, но не учебную эффективность и не готовность к массовому внедрению.

## 9 Что требует доработки

| Приоритет | Проблема | Почему важна | Решение до пилота |
|---|---|---|---|
| P0 | Нет полноценного школьного управления доступом | Свободная роль учителя подходит только для теста | Добавить подтверждение учителя, приглашения, отзыв доступа и журнал событий |
| P0 | Нет восстановления пароля и политики хранения | Потеря аккаунта и лишние данные создают риск | Согласовать восстановление, сроки хранения и удаление |
| P0 | Python является самопроверкой в браузере | Отчёт и эвристика не являются защищённой оценкой | Оставить тренировкой, оценивание делать учителю или отдельной среде |
| P0 | Реальное размещение не подтверждено полностью | Docker и Caddy — комплект, а не работающий VPS | Провести тест на VPS с DNS, TLS, backup и восстановлением |
| P1 | Методические тексты и казахские термины требуют вычитки | Технический перевод не равен педагогической редактуре | Проверить уроки с руководительницей и учителем информатики |
| P1 | Нет исследования учеников | Нельзя доказать, что визуализация помогает | Провести пилот с наблюдением, pre post тестом и интервью |
| P1 | SQLite и один процесс | Подходит одному пилоту, не массовой школе | Зафиксировать пределы, затем решить вопрос миграции по измерениям |
| P2 | Нет истории отправок и аудита учителя | Сложно восстановить, кто и когда менял работу | Добавить версии submission и журнал действий при необходимости |
| P2 | 3D может отвлекать | Объём повышает сложность не для каждой темы | Сравнить 2D и 3D по отзывам учеников |
| P2 | Не завершены accessibility и нагрузочные проверки | Проектор и реальный класс создают другие условия | Проверить клавиатуру, NVDA, мобильный экран и одновременный класс |

Сейчас проект можно описывать как работающий учебный прототип и основу диплома. Нельзя описывать его как готовую государственную платформу, защищённую систему оценивания или доказанно эффективный курс без дополнительных исследований.

## 10 Правила безопасного развития

### 10.1 Если добавляется новый алгоритм

1. Определить учебную цель и минимальный пример.
2. Добавить чистую функцию в `core.js`, которая возвращает шаги, а не HTML.
3. Описать снимок: текущая вершина, очередь или стек, расстояния, активные рёбра, объяснение и итог.
4. Добавить независимый тест с оракулом: недостижимая цель, цикл, равные варианты и ошибочный ввод.
5. Только затем подключать UI и текстовые состояния.
6. Добавить русские и казахские сообщения, не меняя идентификаторы и правильные ответы.

### 10.2 Если добавляется новое занятие

1. Не переиспользовать номер учебного плана. Внутренний порядок 01–15 и номера 17–32 имеют разные смыслы.
2. Добавить занятие в `course.js`, цель, вводный текст, задачу, вопросы и режим алгоритма.
3. Добавить перевод и проверить параметры динамических сообщений.
4. Проверить переходы с карты, главного экрана, предыдущего и следующего занятия.
5. Добавить сценарий учителя: занятие назначается и результат отображается.

### 10.3 Если добавляется серверная функция

1. Определить владельца объекта: учитель, ученик, член класса или система.
2. Проверить роль и принадлежность на сервере. Нельзя доверять `classId` или `userId` из браузера.
3. Решить, нужна ли новая таблица, а не неструктурированное поле.
4. Продумать удаление аккаунта, экспорт, backup, восстановление и срок хранения.
5. Добавить тесты успешного запроса, чужого объекта, отсутствующей сессии, CSRF и повреждённого тела.

### 10.4 Если добавляется язык

1. Добавлять ключи в i18n и locale-файлы.
2. Не переводить имена пользователей, код, комментарии и динамические идентификаторы.
3. Проверить длину текста в карточках, графе, кнопках и режиме показа.
4. Попросить носителя языка проверить предметную терминологию.

### 10.5 Если меняется Pages или hosting

1. Запустить `build-pages.mjs` и `static-demo.test.mjs`.
2. Не копировать `.local`, secrets, SQLite, CNAME и серверные файлы в артефакт.
3. Проверить, что `staticDemo` не вызывает `/api` и скрывает аккаунтные функции.
4. После публикации открыть новый URL в чистой вкладке и пройти карту и один урок.
5. Для VPS отдельно проверить HTTPS, runner на другом имени, backup и восстановление.

## 11 План развития по приоритетам

| Этап | Цель | Работы | Критерий готовности |
|---|---|---|---|
| 0 | Подготовить показ руководительнице | Методическая вычитка 3–5 уроков, свежая ссылка, сценарий 15–20 минут | Рецензент проходит путь без объяснений автора |
| 1 | Провести пилот | Закрытый VPS или локальный класс, тестовые аккаунты, два профиля браузера | Учитель назначает урок, ученик отправляет работу, комментарий возвращается |
| 2 | Укрепить учебный контур | Исправить терминологию, добавить диагностику, сравнить 2D и 3D, улучшить миссию | Есть данные до и после и понятны затруднения |
| 3 | Подготовить диплом | Версионирование контента, история отправок, политика данных, accessibility и нагрузка | Есть обоснованная архитектура и измеримые результаты |
| 4 | Рассматривать масштабирование | Только после измерений: PostgreSQL, очереди, отдельное хранилище и мониторинг | Пределы SQLite подтверждены нагрузкой |

Не следует начинать с рейтингов, сложных бейджей, микросервисов или полного 3D-редактора, пока не подтверждены базовые учебные сценарии. Они увеличат поверхность системы, но не докажут, что ученику понятнее BFS, DFS и кратчайший путь.
## 12 Проверки перед релизом

### 12.1 Чеклист разработчика

- [ ] Изменение описано в одном месте ответственности.
- [ ] Алгоритмическая логика не зависит от DOM, localStorage или сети.
- [ ] Добавлены тесты на обычный, граничный и ошибочный сценарий.
- [ ] Проверены русский и казахский языки, включая длинные строки.
- [ ] Проверены гость, ученик и учитель, если функция касается ролей.
- [ ] Проверены экспорт, удаление, backup и восстановление, если меняются данные.
- [ ] Запущены `node --test` и static-demo тесты.
- [ ] Собран Pages-артефакт без базы, секретов и API-зависимости.
- [ ] Зафиксированы ограничения и версия.

### 12.2 Чеклист учителя

- [ ] Понятно, с какого экрана начинать.
- [ ] Урок объясняет одну идею и даёт одно проверяемое действие.
- [ ] Цвета помогают отличить состояние, а не просто украшают экран.
- [ ] Подписи графа читаемы на проекторе.
- [ ] Ошибка ученика получает объяснение, а не только красный цвет.
- [ ] Python-проверка не воспринимается как официальная оценка.
- [ ] Учитель понимает, где назначить работу и оставить комментарий.
- [ ] Есть способ сообщить о неточном переводе или формулировке.

### 12.3 Сценарий быстрой проверки

1. Открыть главный экран и карту курса.
2. Найти занятие 19, сделать два шага BFS, вернуться назад и предсказать следующий.
3. Переключить русский и казахский, убедиться, что шаг не потерялся.
4. Открыть миссию BFS, сделать одну ошибку и исправить её.
5. В серверной версии проверить цепочку учитель → класс → ученик → работа → комментарий.
6. Сделать экспорт и убедиться, что в нём нет пароля и лишних данных.

## 13 Глоссарий

| Термин | Простое объяснение |
|---|---|
| Граф | Набор вершин и связей между ними |
| Вершина | Отдельная точка или объект графа |
| Ребро | Связь между двумя вершинами; в направленном графе дуга со стрелкой |
| Путь | Последовательность допустимых переходов от одной вершины к другой |
| BFS | Обход слоями: сначала ближайшие вершины, затем следующий уровень |
| DFS | Обход в глубину: идти дальше, пока возможно, затем возвращаться |
| Дейкстра | Поиск пути с минимальной суммой положительных весов |
| Трассировка | Последовательность снимков, описывающих работу алгоритма |
| Рендеринг | Показ текущего состояния на экране |
| Origin | Схема, по которой браузер и сервер проверяют источник запроса |
| CSRF | Токен, защищающий изменяющие запросы авторизованного пользователя |
| Runner | Отдельная среда для выполнения Python в браузере |
| Статическое демо | Версия без API и аккаунтов, работающая в браузере |
| Миграция | Контролируемое изменение структуры базы с сохранением данных |
