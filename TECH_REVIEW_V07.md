# Проверка подготовки к хостингу · 0.7

Дата: 8 октября 2026 года. Версия подготовлена для постоянного размещения
закрытой демонстрации автором и руководительницей на одном Linux VPS.
Сам сайт ещё не размещён. Инструкция: [DEPLOYMENT.md](DEPLOYMENT.md).

## Что изменено

- Node.js 24, Docker Compose и Caddy: два HTTPS-имени, приватная сеть приложения,
  постоянные тома SQLite и сертификатов, автоматический перезапуск, ограничения
  памяти и журналов. Приложение и копирование работают без root.
- Явные настройки origin и Host, отдельный Python runner без API, дополнительный
  пароль демонстрации из файла. Cookies аккаунтов в режиме demo имеют Secure,
  HttpOnly, SameSite=Strict и префикс `__Host-`.
- Проверка готовности приложения, базы и runner; ограничение частоты входов с
  корректным IP за доверенным прокси; очистка истёкших сессий; ограничение размера
  JSON и времени HTTP-запросов; корректное завершение сервера.
- Исправлена гонка одновременной регистрации одного логина. Некорректный JSON,
  включая `null`, массивы и слишком большие тела, возвращает контролируемые 4xx.
- Согласованные ежедневные SQLite-снимки учитывают WAL. Завершённый снимок
  проверяется и публикуется атомарно; сохраняются последние 14 копий по умолчанию.
  Восстановление создаёт новый файл и отказывается заменять существующую базу.
- Клиент ограничивает ожидание API, объясняет сетевые ошибки на двух языках,
  позволяет повторить подключение и вход, сохраняя аккаунт и черновик.
  Неудавшиеся изменения не отправляются повторно автоматически.

## Автоматические проверки

Полный `node --test` на Windows, Node.js 24.19.0: **69 тестов, 69 успешно**.
Тот же набор прошёл в Linux-контейнере Node.js 24.21.0: **69 успешно, без пропусков**.
Тесты используют отдельные временные базы и не меняют рабочую `.local/`.

Проверяются алгоритмы, миссия, переводы, сохранения, права API и следующие
сценарии размещения:

- Внешний пароль, Secure cookies, ожидаемые Host/Origin, изоляция runner,
  недоступность приватной статики без входа.
- Healthcheck, секрет из файла, границы доверия к IP, срок и размер rate limiter,
  oversized Content-Length и chunked JSON, параллельная регистрация.
- Перезапуск: сохранение действующей сессии и удаление истёкшей.
- Live WAL backup, отказ на повреждённом источнике, retention, одновременные
  ручная и плановая копии, восстановление в новый файл, старые и будущие даты
  снимков, параметры планировщика.
- Таймаут загрузки и чтения ответа API, HTML от прокси, отличия ошибок внешнего
  и внутреннего входа, отсутствие автоматических повторных отправок.

`docker compose --env-file .env.hosting.example config --quiet` выполнен успешно
официальным Compose 5.6.0. Проверка конфигурации не запускает контейнеры.

[GitHub Actions · Hosting checks](https://github.com/9dmssi1/Innovation/actions/runs/37822934410)
успешно завершён для commit `22a89ac`. На Ubuntu проверены:

- сборка отдельного тестового образа и runtime-образа;
- полный набор тестов без внешней сети и с read-only файловой системой;
- конфигурация Compose и `caddy validate` в контейнере;
- запуск `app` и `backup` с реальными ограничениями Compose и состоянием healthy;
- внешний пароль, флаги cookie и отсутствие API у runner;
- сохранение аккаунта после принудительного пересоздания контейнера приложения;
- ручной SQLite-снимок и проверка готовности резервного копирования.

Первый запуск обнаружил несовместимость проверочного скрипта с `fetch` новой
версии Node.js: заданный Host заменялся внутренним адресом. Скрипт переведён на
`node:http`, чтобы проверять запросы с тем же публичным Host, который сохраняет
Caddy. Проверка адреса в приложении не ослаблялась.

## Проверки в браузере

В отдельной локальной копии с вымышленным аккаунтом:

1. Сессия принудительно истекла перед сохранением Python-работы. Код и пояснение
   сохранились; появилось предложение повторно войти.
2. Неверный пароль оставил форму и черновик на месте. Верный пароль восстановил
   тот же аккаунт и экран. До отдельного нажатия «Сохранить» записи работы в базе
   не было; последующее сохранение прошло успешно.
3. Тестовый прокси вернул HTML 503. Интерфейс показал понятную ошибку на русском
   и казахском без внутреннего текста прокси и без локальной инструкции START
   для внешнего имени. После восстановления API кнопка повторного подключения
   открыла курс.
4. Переключение языка сохранило код и пояснение. Готовый пример BFS прошёл
   **8 из 8** Python-проверок через изолированный runner.

## Границы проверки и дальнейший запуск

На этом компьютере нет работающего Docker Engine; сборка и совместный запуск
Linux-контейнеров проверены в GitHub Actions, а не на компьютере автора.
Workflow [Hosting checks](.github/workflows/hosting.yml) будет повторять эти
проверки при следующих изменениях. Caddy в CI проходит проверку конфигурации,
но настоящие публичные сертификаты для тестовых имён не запрашиваются.

До передачи ссылки необходимо запустить комплект на выбранном VPS, проверить
DNS и реальные TLS-сертификаты, Python iframe через HTTPS, доступ с другого
компьютера, пересоздание контейнера и пробное восстановление. Команды и порядок
действий приведены в DEPLOYMENT.md. Нагрузочные измерения для целого класса пока
не проводились.

Резервные копии создаются автоматически на том же VPS. Их регулярная отправка
во внешнее защищённое хранилище и уведомления о сбоях требуют настройки на
выбранном хостинге. Наличие локальных снимков не защищает от потери всего VPS.

Учитель по-прежнему выбирает роль при регистрации; восстановления пароля по
почте нет, миссии сохраняются в браузере. Подготовка хостинга не заменяет
методическую проверку, управление допуском учителей и подготовку к работе
с настоящими данными школьников.
