# Постоянное размещение закрытой платформы

В проекте подготовлен комплект для **одного Linux VPS**: Docker Compose запускает приложение, ежедневное резервное копирование и Caddy для HTTPS. Это инструкция по размещению; наличие файлов в репозитории не означает, что сайт уже опубликован.

Режим предназначен для закрытой проверки автором и руководительницей. Для запуска с настоящими школьниками ещё необходимы методическая проверка, правила обработки данных, управление доступом учителей и проверка нагрузки.

Локальный запуск не изменился: `START.cmd` либо `node server.mjs`, Node.js 22.13+. Для хостинга и резервного копирования используется Node.js 24 внутри Docker; устанавливать Node.js на VPS отдельно не нужно.

## 1. Что подготовить

- Linux VPS с постоянным диском и административным доступом. **2 ГБ RAM — стартовая рекомендация для закрытого пилота**, а не обещание определённого числа одновременных учеников. Следите за свободным местом: база, её копии и Docker-образы занимают диск.
- Docker Engine 25+ и Docker Compose 2.24+. Установка на Ubuntu: [официальная инструкция Docker](https://docs.docker.com/engine/install/ubuntu/). Нужен Compose plugin с командой `docker compose`, а не старый `docker-compose`.
- Два разных DNS-имени, например `classroom.example.com` и `python.example.com`. В панели домена направьте A-записи обоих имён на IPv4 VPS. AAAA-запись добавляйте только при работающем IPv6 на этом сервере.
- Входящие TCP-порты **80 и 443** должны быть доступны для Caddy и получения сертификатов; UDP 443 используется для HTTP/3. SSH оставьте доступным администратору. Порты **4318 и 4319 не публикуются** и не должны быть открыты снаружи.
- Доступ сервера к GitHub для скачивания исходников. Для публичного репозитория вход не нужен. Если позднее репозиторий станет приватным, настройте SSH deploy key только для чтения или войдите через штатный инструмент. Не вставляйте токен в URL репозитория, команды, README или переписку.

Проверьте установленное окружение:

```sh
docker version
docker compose version
```

Все команды ниже выполняются в **Bash на VPS**, из одной и той же папки проекта. Если текущему пользователю недоступен Docker, используйте `sudo docker ...` вместо `docker ...`. Не меняйте имя Compose-проекта `innovation`: от него зависят имена постоянных томов.

## 2. Как это устроено

| Сервис | Назначение | Данные |
| --- | --- | --- |
| `app` | Платформа на внутреннем порту 4318; изолированный Python runner на 4319 | SQLite в постоянном томе `classroom_data` |
| `backup` | Согласованные копии работающей SQLite, включая WAL | Отдельный постоянный том `classroom_backups` |
| `caddy` | Два HTTPS-адреса, сертификаты и передача запросов приложению | Постоянные тома сертификатов и конфигурации |

Caddy принимает интернет-трафик. `app` доступен только через внутреннюю Docker-сеть. `backup` не имеет сети. Оба Node.js-сервиса работают от пользователя UID/GID 1000 с доступными для записи томами данных. Корневая файловая система контейнеров доступна только для чтения.

Сохраняйте **один экземпляр `app`**. Текущая архитектура использует SQLite и ограничения частоты запросов в памяти одного процесса; автоматическое масштабирование на несколько экземпляров не настроено.

Два имени необходимы для изоляции Python от аккаунтов платформы. Разных путей или портов одного имени недостаточно: cookies не изолируются по номеру порта. Runner открыт для загрузки iframe, но не отдаёт API, аккаунты и работы учеников. Python выполняется в браузере; браузеру нужен интернет для загрузки Pyodide с jsDelivr.

Внешний адрес всегда берётся из настроек. Внутренний заголовок IP для ограничения частоты запросов Caddy перезаписывает сам. Не публикуйте `app` напрямую и не переносите `GRAPH_TRUST_PROXY=1` в конфигурацию без этого доверенного прокси.

## 3. Скачать проект и заполнить настройки

Клонируйте репозиторий в новую папку:

```sh
git clone https://github.com/9dmssi1/Innovation.git
cd Innovation
cp --no-clobber .env.hosting.example .env.hosting
chmod 600 .env.hosting
nano .env.hosting
```

Если `.env.hosting` уже существует, **редактируйте его**, не заменяйте шаблоном. Заполните:

```dotenv
APP_HOST=classroom.example.com
RUNNER_HOST=python.example.com
ACME_EMAIL=your-email@example.com
DEMO_USER=reviewer
IMAGE_TAG=release-0.7-first
DB_FILENAME=classroom.sqlite
BACKUP_INTERVAL_HOURS=24
BACKUP_KEEP=14
```

Замените имена и почту своими. `APP_HOST` и `RUNNER_HOST` — только имена: без `https://`, портов, пути и завершающего `/`. `ACME_EMAIL` используется для уведомлений по сертификатам. `DEMO_USER` содержит 3–64 латинских символа, цифры, `_`, `.` или `-`.

`IMAGE_TAG` — ваша метка этой сборки: используйте новую метку при обновлении, чтобы сохранить предыдущий Docker-образ для отката. `DB_FILENAME` — имя файла внутри `/data`, без каталогов; при первом запуске оставьте `classroom.sqlite`. Полный путь `/data/имя.sqlite` получает и приложение, и сервис копирования.

Файлы `.env.hosting`, `secrets/` и `backups/` исключены из Git. Шаблоны `.env*.example` не должны содержать настоящих паролей. Docker получает только явно разрешённые исходники: локальная `.local/classroom.sqlite` не отправляется в образ.

## 4. Создать пароль закрытой демонстрации

Следующие команды создают случайный пароль в отдельном файле. Он не попадает в переменные окружения контейнера или историю команд. Режим `noclobber` не позволит заменить уже существующий файл. Выполните этот блок **один раз** при первом размещении:

```sh
mkdir -p secrets
sudo chmod 0700 secrets
sudo bash -c 'set -e; set -o noclobber; umask 077; openssl rand -hex 32 > secrets/demo_password.txt'
sudo chown 1000:1000 secrets secrets/demo_password.txt
sudo chmod 0700 secrets
sudo chmod 0400 secrets/demo_password.txt
```

Владелец 1000:1000 нужен, чтобы файл мог прочитать пользователь контейнера. Для файловых Compose secrets переназначение UID/GID в описании секрета не заменяет права исходного файла на Linux.

Проверьте свой UID командой `id -u`. Если это не 1000, выполняйте команды Docker Compose через `sudo`: закрытый каталог секрета может быть недоступен вашему пользователю при проверке путей. Не расширяйте права каталога до 0755 ради обхода этой проверки.

Если генерация сообщает, что файл существует, не удаляйте его: пароль уже создан. Для просмотра администратором на своём экране можно выполнить `sudo cat secrets/demo_password.txt`. Сохраните пароль в менеджере паролей и передайте руководительнице через согласованный личный канал. Не прикладывайте его к GitHub Issues, скриншотам или логам проверки.

Платформа имеет **два уровня входа**:

1. Браузер сначала запрашивает `DEMO_USER` и пароль из файла — общий доступ к закрытой демонстрации.
2. Внутри платформы используются отдельные аккаунты учителя и ученика, с другими паролями.

Публичные исходники в GitHub не открывают доступ к размещённой демонстрации: эти два входа остаются отдельными. Для первых проверок создавайте вымышленные тестовые аккаунты.

## 5. Первый запуск

```sh
docker compose --env-file .env.hosting config --quiet
docker compose --env-file .env.hosting build --pull app
docker compose --env-file .env.hosting up -d --wait --wait-timeout 180
docker compose --env-file .env.hosting ps
docker compose --env-file .env.hosting logs --tail=100 app backup caddy
```

При первом старте приложение создаст **новую базу** в постоянном томе. Не загружайте на сервер локальную базу с компьютера без отдельного решения о её содержимом.

У `app` и `backup` должны появиться состояния `healthy`. У Caddy в этой конфигурации нет отдельного healthcheck; состояние `running` само по себе ещё не подтверждает получение сертификата. Откройте оба реальных адреса через HTTPS и проверьте браузерный сценарий ниже. Caddy получает и обновляет сертификаты автоматически при правильно настроенных DNS и доступности портов. [Требования Automatic HTTPS](https://caddyserver.com/docs/automatic-https).

После перезагрузки VPS контейнеры запускаются автоматически при работающем Docker. Для обычного перезапуска:

```sh
docker compose --env-file .env.hosting restart
```

После изменения `.env.hosting` нужен `up`, чтобы пересоздать сервисы с новыми настройками:

```sh
docker compose --env-file .env.hosting up -d --wait --wait-timeout 180
```

Для остановки без удаления данных:

```sh
docker compose --env-file .env.hosting stop
```

**Не выполняйте `down -v`, `docker volume prune` или удаление томов ради перезапуска.** Это может удалить базу, резервные копии и сертификаты. Обычные обновления используют существующие тома.

## 6. Проверка по настоящей ссылке

После размещения проверьте с другого компьютера:

1. Без внешнего пароля основной сайт и API закрыты; правильные данные открывают курс.
2. Регистрация, вход и выход работают. Создайте учителя и ученика в двух разных браузерных профилях.
3. Пройдите цепочку: учитель создаёт класс → ученик присоединяется → учитель назначает урок → ученик сохраняет работу → учитель оставляет комментарий.
4. Русский и казахский интерфейсы, BFS/DFS/Дейкстра, шаг назад и 3D работают.
5. Python загружается с отдельного HTTPS-имени; готовый пример BFS проходит 8 из 8 проверок.
6. После `restart` аккаунты и сохранённая работа остаются. Отдельно проверьте пересоздание приложения с тем же томом:

```sh
docker compose --env-file .env.hosting up -d --force-recreate --no-deps --wait app
```

7. Сессия приложения использует cookie с `Secure`, `HttpOnly`, `SameSite=Strict` и префиксом `__Host-`; она не отправляется на имя runner. На адресе Python нет API и содержимого базы.
8. В сервисе `backup` появилась согласованная копия. Выполните пробное восстановление в новый файл по разделу ниже.

## 7. Резервные копии и хранение вне VPS

Сервис делает первую копию сразу после запуска, затем раз в 24 часа. Он использует SQLite online backup API: копия включает подтверждённые изменения из WAL. Перед публикацией файла выполняются `quick_check` и проверка наличия таблиц. Копирование одного файла работающей базы обычным `cp` этого не гарантирует.

По умолчанию сохраняются **14 последних снимков, а не гарантированно 14 дней**: ручной запуск и перезапуск сервиса создают дополнительные копии. `BACKUP_KEEP` допускает 1–365, `BACKUP_INTERVAL_HOURS` — целое число часов 1–168. При переводе часов назад утилита может оставить один дополнительный свежий снимок. Удаляются только файлы собственного точного шаблона; незавершённая копия не запускает удаление старых.

Проверка и ручная копия:

```sh
docker compose --env-file .env.hosting exec backup node scripts/backup-healthcheck.mjs
docker compose --env-file .env.hosting exec backup node scripts/backup.mjs
```

Вторая команда выводит **точный путь** вида `/backups/graph-classroom-ДАТА-UUID.sqlite`. Скопируйте именно этот файл; ниже `EXACT_FILE.sqlite` нужно заменить его полным именем без `/backups/`:

```sh
mkdir -p backups
chmod 0700 backups
docker compose --env-file .env.hosting cp backup:/backups/EXACT_FILE.sqlite ./backups/EXACT_FILE.sqlite
chmod 0600 ./backups/EXACT_FILE.sqlite
```

Это всё ещё копия **на том же VPS**. При потере диска она исчезнет вместе с платформой. Скачайте её на свой компьютер или в отдельное защищённое хранилище. Пример команды, выполняемой **на своём компьютере**, с заменой пользователя, адреса и пути:

```sh
scp ADMIN@SERVER_IP:/home/ADMIN/Innovation/backups/EXACT_FILE.sqlite ./EXACT_FILE.sqlite
```

В копии есть аккаунты и работы, поэтому не загружайте её в GitHub и не передавайте участникам проверки. Храните вне VPS также закрытый доступ к настройкам и секрету, отдельно от исходников. Настройте регулярное внешнее копирование средствами выбранного хостинга/хранилища: текущий комплект автоматически создаёт снимки на VPS, но **не загружает их во внешнее облако**.

Healthcheck резервного копирования обнаруживает отсутствие копий, устаревший снимок и некорректную дату в будущем. Ошибка копирования завершает сервис с ненулевым кодом, после чего Docker его перезапускает. Уведомления владельцу по почте пока не подключены: регулярно проверяйте `ps`, логи и свободное место.

## 8. Восстановление без перезаписи рабочей базы

Восстановление выполняется в период, когда никто не работает с платформой. Сначала сохраните свежий снимок текущей базы, если она ещё читается, и его копию вне VPS. Запишите текущее `DB_FILENAME` из `.env.hosting`.

Остановите приложение и плановое копирование; остановка Caddy уберёт внешний доступ на время работы:

```sh
docker compose --env-file .env.hosting stop caddy backup app
```

Выберите проверенную копию в `/backups`. Укажите **новое уникальное имя**, например `restored-20261008-120000.sqlite`, которое ещё не существует. Замените в команде пример имени и `EXACT_FILE.sqlite`:

```sh
docker compose --env-file .env.hosting run --rm --no-deps backup node scripts/restore.mjs /backups/EXACT_FILE.sqlite /data/restored-20261008-120000.sqlite
```

Одноразовый контейнер не запускает планировщик и не поднимает приложение. Утилита проверяет копию и отказывается работать, если целевой файл или его `-wal`, `-shm`, `-journal` уже существуют. Она не удаляет текущую базу и не заменяет её содержимое.

Только после успешного завершения откройте `.env.hosting` и поменяйте:

```dotenv
DB_FILENAME=restored-20261008-120000.sqlite
```

Затем запустите сервисы и проверьте аккаунт и сохранённую работу:

```sh
docker compose --env-file .env.hosting up -d --wait --wait-timeout 180
```

И приложение, и планировщик начнут использовать восстановленный файл. Старый файл и его служебные файлы остаются в томе. Если выбран неверный снимок, снова остановите сервисы, верните прежний `DB_FILENAME` и запустите их. **Не удаляйте WAL/SHM и не копируйте старую базу поверх новой.**

Если нужный снимок есть только на вашем компьютере, сначала загрузите его на VPS через `scp` в `backups/`. Для импорта в том выполните команды ниже из папки проекта, пока сервисы остановлены. Префикс `sudo` нужен, чтобы сохранить владельца 1000:1000 при копировании; имя `imported-EXACT_FILE.sqlite` должно быть новым:

```sh
sudo chown 1000:1000 ./backups/EXACT_FILE.sqlite
sudo chmod 0600 ./backups/EXACT_FILE.sqlite
sudo docker compose --env-file .env.hosting cp --archive ./backups/EXACT_FILE.sqlite backup:/backups/imported-EXACT_FILE.sqlite
```

При восстановлении на совершенно новом VPS сначала подготовьте настройки, секрет и Docker-образ по разделам 1–5, затем остановите сервисы. После импорта используйте `/backups/imported-EXACT_FILE.sqlite` в команде `restore.mjs` выше. Сначала всегда восстанавливайте в новое имя, проверяйте результат и только потом переключайте `DB_FILENAME`.

## 9. Обновление и откат версии

Перед обновлением:

1. Сделайте ручной снимок и скачайте его вне VPS.
2. Запишите `git rev-parse HEAD`, текущие `IMAGE_TAG` и `DB_FILENAME` в закрытые заметки администратора. Не удаляйте предыдущий Docker-образ.
3. Проверьте `git status --short`. Если есть собственные изменения исходников, сначала сохраните их и разберите конфликт; не используйте принудительный сброс.

Обновление исходников и сборка:

```sh
git switch main
git pull --ff-only
git rev-parse --short HEAD
nano .env.hosting
```

В `.env.hosting` поменяйте `IMAGE_TAG` на новую метку, например `release-НОВЫЙ_COMMIT`. Сохраните существующие адреса, секрет и `DB_FILENAME`.

```sh
docker compose --env-file .env.hosting config --quiet
docker compose --env-file .env.hosting build --pull app
docker compose --env-file .env.hosting up -d --wait --wait-timeout 180
```

Проверьте HTTPS, вход, сохранение работы и Python. Сборка сама по себе не заменяет контейнер: если сборка завершилась ошибкой, не переходите к запуску.

Для отката к **предыдущей уже размещённой версии с Compose** верните её исходники и ранее сохранённый `IMAGE_TAG`. `PREVIOUS_COMMIT` ниже — записанный перед обновлением Git commit; команда допустима только при отсутствии несохранённых правок:

```sh
git switch --detach PREVIOUS_COMMIT
nano .env.hosting
docker compose --env-file .env.hosting up -d --no-build --wait --wait-timeout 180
```

Откат Docker-образа **не откатывает данные**. Если обновление меняло схему базы несовместимым образом, сначала остановите сервисы и восстановите снимок в новый файл по разделу 8, затем выставьте его `DB_FILENAME`. Возможность такого отката нужно проверять для каждой будущей миграции. Для возврата к обычному обновлению после проверки используйте `git switch main`.

## 10. Если что-то не запускается

| Симптом | Что проверить |
| --- | --- |
| Ошибка `DEMO_PASSWORD_FILE` | Существование файла, владелец 1000:1000, файл 0400 и каталог 0700 |
| Не выдаётся HTTPS-сертификат | DNS обоих имён, лишняя AAAA-запись, доступность TCP 80/443, логи Caddy |
| `app` не становится healthy | Логи `app`, заполнение `.env.hosting`, разные имена сайта и runner, доступность тома базы |
| `backup` перезапускается или unhealthy | Логи, свободное место, наличие базы, корректные интервалы и права обоих томов |
| Python не загружается | HTTPS runner, отдельное имя, настройки браузера и доступ к jsDelivr |
| После изменения `.env.hosting` поведение прежнее | Выполните `up -d --wait`, а не только `restart` |
| Появилась пустая база | Остановитесь и проверьте `DB_FILENAME`, папку запуска и имя Compose-проекта; не удаляйте старые тома |

## Что проверено, а что ещё требует настоящего сервера

В репозитории есть автоматические тесты приложения и утилит резервного копирования. В [`.github/workflows/hosting.yml`](.github/workflows/hosting.yml) подготовлен GitHub Actions workflow `Hosting checks`: он проверяет Docker-сборку, Compose, Caddy, healthcheck, доступ и сохранение аккаунта после пересоздания приложения. **Подготовленный workflow ещё нужно запустить в GitHub; наличие файла не означает успешный CI.**

Локальные тесты с HTTP-заголовками не проверяют настоящую выдачу TLS-сертификатов, внешний DNS, iframe в размещённом сайте или диск конкретного VPS. Перед передачей ссылки нужно выполнить раздел 6 и пробное восстановление. Даже успешный CI не заменяет эти проверки.

Эта версия остаётся закрытым пилотом: роль учителя выбирается при регистрации, восстановление пароля по почте не настроено, результаты миссий хранятся в браузере. Публичное использование с реальными данными школьников требует отдельной подготовки и согласования.
